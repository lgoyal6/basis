# What happens to the file you upload

You are being asked to upload a record of everything you have bought and sold. That is about
as personal as a document gets, and "trust us" is not an answer. So this page describes what
the code does, and names the file that does it, so you can check rather than believe.

## It is never written to a database

Your statement is held in the server's memory and nowhere else. Not in Postgres, not on disk,
not in a log.

This is a deliberate design decision rather than a shortcut. Deleting a row from a database
does not really delete it: there are backups, replicas and a write ahead log, and a promise
to delete is only as good as all of them. A promise that the data was never written down is
one you can verify by reading
[`SessionStore.java`](src/main/java/com/basis/web/SessionStore.java).

It costs something, and the cost is honest: a redeploy loses every open session, and the
service cannot run on more than one instance. Both were judged acceptable for a flow whose
whole shape is upload, look, leave.

## It is deleted in two hours, or the moment you ask

There is a delete button on the results page. It removes the entry immediately.

If you close the tab and forget, the session expires on its own. Expiry is checked when a
session is read as well as swept in the background, so an expired upload is unreachable at the
instant it expires rather than whenever a cleanup job next happens to run.

## There is no account, so there is nothing to link it to

No email, no password, no signup, no third party sign in.

You get one cookie holding a random 256-bit identifier, which is how the results page finds
your upload again. It is generated by `SecureRandom` and carries no information: it is not a
counter, not a hash of your file, not a timestamp. It means nothing once the session is gone.
The cookie is HttpOnly, SameSite=Lax, signed so a tampered value is rejected rather than
looked up, and marked Secure whenever the request arrived over HTTPS.

## What is counted

Counts by category, and nothing else:

- how many uploads parsed, and which broker format they were
- how many uploads failed, and for which of a fixed set of reasons
- how many breaks were found, of each kind
- how many positions reconciled exactly on the first pass
- how often an ambiguous corporate action was surfaced, and how often somebody chose

No symbols, no quantities, no dates, no filenames, no account numbers, no IP addresses,
nothing that could be joined back to a person or a holding. The counter names are drawn from a
fixed vocabulary, so an upload cannot cause arbitrary text to be recorded.

These exist to answer one question: does this find real errors in real accounts. That is a
question about how many, not about whose.

## What basis never asks for

Your broker login. There is no OAuth, no bank connection, no Plaid, no read only API key.
basis reads files you already have. It cannot see your account, cannot place a trade, and
cannot reach your broker at all, because nothing in it knows how to.

## If you would rather not upload anything

Don't. The same tool runs on your own machine against your own Postgres, and finds exactly the
same breaks, because the web version calls the same ledger code rather than reimplementing it.

```
git clone https://github.com/lgoyal6/basis && cd basis
./scripts/demo.sh
```

The web version exists only because installing a JDK and a database is a lot to ask of
somebody who just wants to know whether their cost basis is wrong.
